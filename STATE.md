- **2026-09-09** — **Unloadable saved scenes are hidden, never auto-deleted.** The owner's editor listed saved scenes that would not open, and his instinct was that "unloadable scenes should get cleaned from db". Filtering the switcher is right; **pruning on init is not**, on two grounds he could not see from the UI: a missing asset blob is frequently recoverable by re-uploading the asset, and **Dexie is per-browser-profile**, so a scene authored in one browser reads as assetless in another while being perfectly intact there — silent deletion would destroy real work in the exact case where the data is fine and only the *view* of it is broken. So `sceneAvailability.ts` classifies (`ok`/`partial`/`unloadable`), the dropdown filters, and removal is an explicit confirm-gated action in the Saved-scenes panel. **An empty scene classifies `ok`**, not unloadable, or every freshly-created scene would disappear from the switcher. Verifying the filter caught a regression it had just introduced: `SceneEditorSavedScenesSection.vue` **was never imported anywhere** — dead code whose own header comment claimed otherwise — so hiding rows from the dropdown left them with no management surface at all; the panel is now genuinely mounted. **Generalized: a filter's failure mode is silently eating good rows, so it ships with a negative control** — one test asserts a fully-resolving scene is never hidden.
- **2026-09-09** — **A gate on an opaque overlay must release in `finally`.** The owner reported the editor "stuck on loading scene" with no grid. Two separate defects share that symptom and only one was his: (1) `loadScene()` set `isReady=false` and restored it only on the success path, so any throw wedged the editor behind a **fully opaque** overlay while the grid, lights and markers rendered invisibly underneath — now try/finally, because a partially-built scene over a visible grid is recoverable and an opaque overlay is not; (2) his actual cause was **`new THREE.WebGLRenderer()` throwing at the first statement of `init()`**, upstream of `loadScene` entirely — my first fix would not have touched it. WebGL was disabled in his Opera (hardware acceleration off → software GL crash-loop → `Disabled Features: all`), proven *not* to be a machine fault by reading WebGL 2 / `ANGLE (AMD Radeon RX 6700 XT, D3D11)` from the Claude pane on the same machine at the same moment. Not a code bug, but the code's response to it was an infinite lie; `init()` now catches and reports the real cause. **Generalized: "I fixed the wedge" is only true for the throw sites the guard actually encloses — check where the throw is before claiming the class is closed.**
- **2026-08-31** — **Structural gate before instance fixes; and `.vue` is measured per SFC block, not whole-file.** The queued question was whether the structural review gate (a linter) should precede reviewing the two ~1,500-line editor Vue components one at a time. Settled **gate first**, and slice 1 shipped the same session — but the deciding evidence was produced by measuring, not by arguing. (1) Measuring the two SFCs *per block* showed they are not the same problem: `SceneEditorInspector.vue` is 1,513 lines yet its **script is 342 and passes**, with the bulk in a 523-line template and a 634-line stylesheet, while `SceneEditorView.vue` carries a genuine **1,057-line script**. A whole-file `wc -l` calls those equivalent and would have frozen a wrong metric into a baseline and a ratchet — so `.vue` is gated per block (script 600 / template 400 / style **ungated**, since CSS is bulk rather than comprehension load and follows the components out on a split). (2) The gate's first run found **7 violations of which 4 were files nobody was tracking**, the largest being `player-three/src/PlayerController.ts` at **1,679 lines** — bigger than either editor SFC. Attention had been on the files that happened to get measured; instance-fixing would never have reached them. Also **corrected the plan's own sequencing rationale**: it argued decomposition must come first so the baseline is not "frozen against today's debt", which does not survive the ratchet — a one-way ratchet records debt and forbids growth, then lowers itself as work lands. Severity **advisory** (a one-session-old metric that blocks gets switched off within a week). Record: `docs/architecture/STRUCTURAL-RULES.md`.

- **2026-08-31** — **Editor decomposition strategy: purity first, then context; and the context carries handles only.** `useSceneEditorViewport.ts` was 2,174 lines / 68 functions in one closure over shared THREE state, so no function could move until that state's boundary was decided. Chose staged extraction over a big-bang context object or sub-composables: stage 1 moves only logic needing *none* of that state (buys testability, not size — the file went 2,174→2,160), stage 2 moves clusters that own their own state. The load-bearing decision is the **layering contract**: L0 pure kernels / L1 owned-state modules / L2 the orchestrating composable, with **no L1→L1 dependency**, and a context that carries **engine handles** (`scene`/`camera`/`renderer`/`controls`/`TC`) but **never cross-cluster state** (selection, place mode, gesture snapshot). Conflating those two is precisely how a shared context becomes the god object relocated rather than removed — the failure mode this plan exists to avoid. Anim delegators (~120 lines) are named as the deliberate cheap validation of that rule before pose/IK (~350) bets on it. Plan of record: `docs/PLAN-EDITOR-DECOMPOSITION-2026-08-31.md`.
- **2026-08-31** — **L0 Asset Gate Q6: split the linter's own severity tiers.** Q3 fixed *which* GLB-linter checks are required but never what they do at the export gate; as built, `glbLinter.ts` marked all three `veto`, so mechanically wiring `lintGlb()` into F-G3 would have made a Blender-default root name (`"Scene"`) a hard export blocker. `named-root` + `scale-sanity` stay veto (they corrupt socket references and downstream world-matrix math); `base-pivot-sanity` becomes advisory (the editor's Y-snap compensates — bad authoring, not corrupt data). Rests on two grounds independent of asset-migration risk (which the owner dismissed): severity belongs in the verdict **data** rather than each call site's discretion — otherwise the export gate, the planned CLI twin and the deferred VLM socket each invent their own reading — and **Q3 already promised a deferred/warn tier**, so an advisory class must exist regardless and an all-veto linter leaves it nowhere to land. Also conformed `glbLinter` to its merged sibling `attachmentValidator`, which already returned three-state severity. Implemented on `auto/f-g5-glb-linter` (`0a76967`).
